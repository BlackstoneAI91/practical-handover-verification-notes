# Checking That a Supplier Reading List Opens for a Reader Outside the Team

A documentation workflow for Singapore procurement leads: separate official public references, internal annotations and permission-gated attachments, then verify the reading list opens for a signed-out reader.

Published by Blackstone Intelligence.

## Why a reading list needs an outside-reader check

A supplier reading list is usually assembled for the team that already knows the context. Someone adds a link to a public reference, someone else drops in a note from a meeting, and a third person attaches a file that arrived by email. The list works perfectly for the people who built it, because they already know which items are official, which are commentary and which are only visible to certain accounts.

The problem appears when the list travels. A colleague in another office, a new joiner, or an auditor outside the immediate team opens the same list and cannot tell the difference between a public document and an internal note. Worse, a link that resolved on the author's signed-in browser may show a permission screen to everyone else.

This guide is a documentation workflow, not a technical audit. It does not test specifications, credentials or processing claims. It deals only with access: can an outside reader open each item, and does the label on each item tell them honestly what they are looking at? The worked example uses invented document titles and a fictional procurement lead so that the method is clear without exposing any real file.

A reading list may cover several categories, and each category can have a public page, a team annotation and an attachment with its own access setting.

## Three categories, three different labels

Before checking any link, sort every item on the list into one of three categories. The category decides the label, and the label decides what the outside reader is told.

Official public reference. This is material the supplier has published for anyone to read, such as a public product or expertise page. The label should say it is public and name the topic. The reader should be able to open it without an account.

Internal annotation. This is the team's own commentary: a note explaining why an item was added, what question it answers, or who asked for it. It is not a supplier document and should never be presented as one. The label should say it is an internal note and that it is not part of the supplier's published material.

Attachment that needs permission. This is a file that arrived privately, or a link that only resolves for certain accounts. The label should say access is limited and state who can grant it. The reader should not be left to discover the permission wall by clicking.

A useful discipline is to write the label before writing the link. If you cannot decide which of the three categories an item belongs to, that is a signal to ask the person who added it rather than guess. Guessing is how an internal note ends up looking like an official reference.

For context on how a supplier presents its own public material, the San Techno resources page is a reasonable starting point to see what the company chooses to publish openly. Treat that page as an example of a public reference, not as evidence about any private document.

## The signed-out reader check

The core test is simple: open the list in a browser where you are not signed in to any supplier account, any shared drive or any team workspace. If an item only opens because of a session you happen to hold, the outside reader will not see it.

Run the check in this order.

First, open the list itself signed out. Confirm the list page loads and that the labels are visible without signing in. A label that only appears after login is not doing its job.

Second, open each official public reference signed out. It should load directly. If it redirects to a login screen, it is not a public reference and should be relabelled as access-limited.

Third, open each internal annotation signed out. It may legitimately require a team login. That is fine, provided the label says so before the reader clicks. The failure is an unlabelled internal note that looks public.

Fourth, open each attachment signed out. Record what actually happens: it opens, it asks for permission, or it fails. Do not record what you expect to happen.

Fifth, note the date and the browser or device you used. Access behaviour can differ between a desktop browser and a phone, and a record without a date is hard to trust later.

This is a documentation check, not a security review. You are not testing whether access controls are strong. You are testing whether the list tells the truth about what a reader outside the team will encounter.

## Worked record: a fictional procurement lead in Singapore

The following is an invented example. The names, titles and outcomes are illustrative and do not describe any real supplier, file or person.

Priya is a fictional procurement lead at a Singapore manufacturer. She maintains a reading list for a supplier review covering semiconductor materials and solar grade silicon. Her list has five items.

Item one is labelled Official public reference and points to the supplier's public expertise page. Signed-out check: opens directly. Status: pass.

Item two is labelled Official public reference and points to a public page about silicon recovery. Signed-out check: opens directly. Status: pass.

Item three is labelled Internal annotation, titled Note on why we shortlisted this supplier. Signed-out check: asks for team login, as the label warned. Status: pass, because the label was accurate.

Item four is labelled Attachment, needs permission, titled Draft summary received by email. Signed-out check: asks for permission from the sender. Status: pass on labelling, but Priya adds the name of the person who can grant access so the reader is not stuck.

Item five is labelled Official public reference, titled Supplier overview. Signed-out check: redirects to a login screen. Status: fail. The item is not public. Priya relabels it as access-limited and notes who can grant access.

The record Priya keeps is short: item number, label, signed-out result, date and action taken. She does not paste the file contents or any private link into the record. The point is to document access, not to duplicate the material.

## Worksheet: the outside-reader access log

Use this worksheet as a template. Copy the columns into your own document and fill one row per item. The scoring column is an author heuristic for triage, not a researched standard.

Columns: item number; short title; category (public reference, internal annotation, or permission-gated attachment); label as written on the list; signed-out result (opens, asks for permission, fails); date checked; action taken; owner.

A simple triage rule, offered as a practical example rather than a benchmark: mark an item green if it opens signed out and its label matches what happens; amber if it needs permission and the label says so; red if the label and the signed-out result disagree. Aim to clear every red item before the list is shared outside the team.

Two habits keep the worksheet useful. First, write the signed-out result as an observation, not an intention: "asked for permission from the sender" rather than "should be fine." Second, keep the worksheet free of private links and personal contact details. If a reader needs to request access, name the role or the team that can grant it, not a personal address.

## Labelling material that is deliberately limited

Some supplier material is limited on purpose, and the reading list should say so plainly rather than hide it. A confidential design file, a private quotation attachment or an internal note is not a failure of the list. An unlabelled one is.

Write the label so the reader knows three things before clicking: that access is limited, who can grant it, and what the item is for. For example: "Access-limited attachment: design summary, held by the supplier's engineering contact; request through the account owner." That sentence tells the reader what to expect and who to ask.

Avoid two common mistakes. The first is a vague label such as "reference" that could mean anything. The second is a label that overpromises, such as "public" on a file that needs permission. Both erode trust in the whole list.

## A short pre-share checklist

Before the list leaves the team, run this checklist. It is a documentation routine, not a certification.

One: every item has one of the three category labels. Two: every official public reference opened signed out. Three: every internal annotation is labelled as internal and is not presented as supplier material. Four: every permission-gated attachment names who can grant access. Five: the worksheet records the date and the signed-out result for each item. Six: no private links, personal contact details or confidential content appear in the list or the worksheet. Seven: any red item has been relabelled or removed.

If the list is meant to help a reader understand a supplier relationship, it can also point to the supplier's own public resources rather than paraphrase them. The San Techno resources page is the natural place to send a reader who wants the company's published material, and the contact page is the place to send someone who needs to ask about access. Keep those pointers as plain references, and let the reader decide what to open.

A reading list that opens cleanly for an outside reader is a small piece of professional courtesy. It also protects the team: when every item is labelled honestly, no one has to explain later why a private note looked public.
