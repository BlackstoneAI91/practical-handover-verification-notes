# Checking a Kuching Website Handover Note Against the Approved Asset List

A practical guide for Malaysian service businesses comparing a public website handover note with the approved list of images and page labels, including a copyable comparison row and a review sequence.

Published by Blackstone Intelligence.

## Why the handover note and the approved list drift apart

A website handover note is written at the end of a project, usually in a hurry. It records what the person writing it believed was true on that day: which image sits in the banner, which page carries the service label, which version of a diagram was uploaded last. The approved asset list is a different kind of document. It is agreed earlier, often in a shared folder or a signed-off spreadsheet, and it describes what the business intended the site to show.

The two documents rarely disagree on purpose. They drift because they are updated by different people at different moments. A designer swaps a photograph because the original was too dark. A writer shortens a page label so it fits a menu. Neither change is wrong, but neither is recorded in both places. By the time the site is live, the handover note describes one version and the approved list describes another.

For a Kuching service business, this matters because the website is often the first place a customer checks before calling. A mismatched image or a page label that no longer matches the printed material creates a small but real doubt. The goal of this check is not to assign blame. It is to find every place where the public site, the handover note and the approved list describe three slightly different things, and then decide which version should stand.

This guide assumes you are reviewing a fictional business with a public site, a handover note and an approved asset list. Nothing here depends on a particular platform, and no conclusion about licensing or ownership is drawn from the comparison itself. Those questions belong to the people who signed the original agreement.

## Set up the three documents before you compare anything

The most common mistake is to start reading the website first. That anchors your attention on whatever is currently live and makes it harder to notice what the approved list actually said. Instead, lay out three things side by side.

First, the approved asset list. This should name each image and each page label in the form the business agreed to use. If it is a spreadsheet, keep the row order intact so you can move through it systematically.

Second, the handover note. This is the document produced at the end of the build. It may be a short memo, a folder readme or a section in a project file. Read it once without comparing, just to understand what it claims to cover.

Third, the public website itself. Open it in a browser and be prepared to look at the same page more than once, because images and labels often appear in more than one place.

Before you begin, decide who will answer questions. A comparison produces questions, not answers. Someone needs the authority to say whether the approved list or the live site is correct. If that person is not available, record the questions and move on rather than guessing.

If the site was built by an external team, the handover note is often the only written record of what was delivered. Treat it as evidence to be checked, not as a description of the approved state. The approved list is the reference; the handover note is a claim about how well the site matches it.

## A copyable comparison row

The comparison is easier to sustain if every finding uses the same shape. One row per asset, with four fields, is usually enough. Copy the pattern below into a spreadsheet and repeat it for each image and each page label.

Asset name or page label | What appears on the public website | What the handover note says | Question for the reviewer

A worked example, using a fictional business, shows how the row behaves in practice.

Banner photograph, service page | A wide photo of a shopfront at dusk | Handover note lists a daytime exterior shot | Which version was approved, and does the approved list name a file or only describe the scene?

Service page label | "Repairs and servicing" | Handover note says "Repair services" | Was the label shortened after approval, and does the printed material use the longer or shorter form?

Team page image | Two people standing beside a counter | Handover note lists a single portrait | Was the group image approved as a replacement, or added without a record?

Diagram on the process page | Three-step diagram with numbered circles | Handover note refers to a four-step diagram | Which diagram is current, and is the older file still stored anywhere public?

The fourth column is the important one. It should always be a question, never a verdict. Writing "wrong image" closes the conversation; writing "which version was approved" opens it. The reviewer can then check the approved list, the original brief or the person who signed off, and the answer becomes part of the record.

Keep the rows in the same order as the approved list. When you finish, the spreadsheet reads as a mirror of the approved list with three extra columns, which makes it easy for someone else to pick up later.

## Checking images against the approved list

Images are where handover notes age fastest. A photograph is easy to replace and easy to forget, and the replacement often happens late in a project when everyone is tired.

Work through the approved list image by image. For each one, find every place it appears on the public site. A banner image may also appear on a category page, in a thumbnail grid or inside a news item. Note each location in the second column rather than assuming one image has one home.

Then compare the description in the handover note. Handover notes often describe an image loosely, for example "exterior shot" or "team photo", without naming a file. That looseness is itself a finding worth recording, because it means the note cannot confirm which version was used.

Pay attention to images that carry text. A diagram, a map or a photo with a caption baked into the image is harder to correct later, and a mismatch there is more visible to a customer than a swapped background. If the approved list names a version number or a date, record whether the live image appears to match it.

Finally, note any image on the public site that does not appear on the approved list at all. An unlisted image is not automatically a problem, but it is a question: was it approved later, and if so, where is that recorded? Leave the answer to the reviewer.

## Checking page labels and navigation text

Page labels are quieter than images but more consequential, because they shape how a visitor understands the structure of the business. A label that reads "Solutions" on the site and "Services" in the approved list is a small inconsistency, but it can confuse someone who was told to look for services.

Start with the main navigation. List every label in order, top to bottom, and compare it with the approved list. Then repeat for the footer, which often carries a second set of labels that nobody checks.

Next, look at headings inside pages. A page may be labelled one way in the menu and another way in its own heading. Both should be recorded, because a visitor sees both.

Then check the labels used in buttons and forms. "Enquire", "Get a quote" and "Contact us" are not interchangeable in every context, and the approved list may specify one. Record what the live site uses and what the handover note claims.

Where a label differs only in punctuation or capitalisation, note it but do not treat it as urgent. Where a label differs in meaning, such as a page that promises a service the approved list does not include, flag it clearly in the question column. That is the kind of difference a reviewer needs to resolve before the next round of printed material goes out.

If the site is being reviewed as part of a wider refresh, the same discipline applies to any new pages. A team providing web design services in Kuching will usually welcome a clear list of label questions, because it turns a vague request into a specific correction.

## Handling mismatches without reopening the whole project

A comparison will produce a list of differences, and the temptation is to treat every difference as a defect. Resist that. Most mismatches fall into three groups, and each deserves a different response.

The first group is documentation lag. The site is correct and the handover note is out of date. The fix is to update the note, not the site. Record the correction and move on.

The second group is an unrecorded change. The site differs from both the approved list and the handover note. This needs a decision from whoever owns the approved list. Until that decision is made, mark the row as open and do not change the live site.

The third group is a genuine error. The site shows something the approved list explicitly rules out. These are usually few, and they should be fixed first because they carry the most risk of confusing a customer.

A simple scoring habit helps prioritise without pretending to be research. For example, an author heuristic might score each row from one to three: one for a cosmetic difference, two for a label that changes meaning, three for an image or label that contradicts the approved list outright. Sort by score and work down. Treat the scale as a personal sorting aid, not a standard anyone else must adopt.

Set a review window as an example only, such as one working week for a small site, and adjust it to the size of the list. The point is to close the loop while the people who remember the decisions are still reachable.

## Keeping the record useful after the review

The comparison spreadsheet is worth more than the review that produced it, provided it is stored where the next person can find it. Save it beside the approved list rather than in a separate folder, and name it with a date so later versions do not overwrite it.

Add a short closing note to the handover document itself. It does not need to be formal: a line stating that the site was compared against the approved list on a given date, with a pointer to the spreadsheet, is enough. That single line turns a static handover note into a record with a history.

When the site next changes, repeat the comparison against the same approved list, or against a new version if one has been agreed. The row structure stays the same, so the second review is faster than the first.
